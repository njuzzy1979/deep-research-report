写作和数据图表**同步推进**——每完成一章的文字草稿，立即产出该章的数据图表。这样图表与文字在同一个上下文中形成，不会出现脱节。

## 7.0 卡片到正文的叙事化转写

卡片是研究笔记，正文是论证性写作。转写的核心原则：

**1. 以论点为主线，不以卡片为主线**
- 先确定本节要论证什么（来自大纲的"本节要论证什么"）
- 从卡片中选取支撑论点的素材
- 一张卡片的不同字段可以分散在本节的不同位置
- 不要求每张卡片都被正文引用——不是所有调研成果都要入正文

**2. 四条转写铁律**
- **禁止将卡片的字段逐条翻译为段落**：案例卡的"时间线/背景问题/关键动作/技术支撑/效果/风险争议/可提炼机制"是分析框架，不是正文的7个自然段
- **禁止在正文中出现字段标签**：正文中不应出现"时间线：2022年..."、"效果（量化优先）：增长240%"这类卡片模板痕迹
- **每条关键判断必须呈现完整的三角结构**：主张→证据→推理。卡片提供了"证据"那一角，写作时补全"主张"和"推理"。**⚠ 三角的"证据"角指的是可追溯的事实来源（机构+日期+数据），不是"这条证据的等级评价"或"核验取舍过程"。把证据分级/取舍当成"证据"角写进正文，是本铁律最常见的误用**（见 `writing-standards.md` 标准 0）
- **禁止把后台过程当正文**（已由素材阶段物理隔离兜底）：证据等级评价、来源取舍、核验状态自述、claim_id、方法论自评均属内部质控元数据（见 `writing-standards.md` 标准 0）。素材阶段的搜集甄别（阶段 2 §2.0.1）已剔除不可信来源、核验后二分决策（阶段 3 §3.3）已将剔除的主张物理隔离于卡片池之外，Writer 接触到的素材均为已检验的 adopted=true 主张。如 Writer 仍接触到分级信息，说明管线有 bug。判定测试：删掉这句话，读者对"发生了什么 / 结论是什么"的理解是否受损？不受损 → 是元数据，从正文中移除

**3. 卡片到段落的正确转写路径**

| 卡片字段组合 | 正文转写产物 | 示例 |
|------------|------------|------|
| 时间线 + 背景问题 + 关键动作 | 案例叙述段落（按时间或因果展开） | "2022年SpaceX首次演示...随后在2023年..." |
| 核心概念 + 输入输出 + 关键数据 | 技术机制阐述段落 | "TLE轨道数据通过SGP4模型传播后..." |
| 可提炼机制 / 关键数据 | 观点/结论段落（作为论证的"证据"角） | "这表明AI云探测已在时效性上超越传统方法..." |
| 风险争议 + 局限 | 边界/不确定性说明段落 | "然而该方案在低轨目标上的精度仍受限于..." |

**4. used_in_chapter 回填的强制执行**
- 写完一章后，必须逐张检查本章对应的卡片（通过 card-index.csv 的 `chapter_ref` 字段）
- **引用了的卡片**：在 `used_in_chapter` 填入章节号（如"第3章"）
- **未引用的卡片**：在 `card-index.csv` 的 `notes` 列注明原因（如"素材重复""与本章论点无关""证据不足弃用"）
- 阶段7质量门槛第5项强制执行此检查

> **反例警示**：如果正文中出现了"时间线：2023年X月..."、"关键动作：部署..."这样的字段标签式写作，说明写作者是在"翻译卡片"而非"用卡片论证"——退回到本节重新理解"以论点为主线"原则。

**5. 卡片关系字段→叙事衔接的转写指引**

卡片模板里有"与其他组件关系""与其他概念关系"这类关系字段。它是**给写作者理解知识结构用的思维辅助**，不是要转写成正文里的坐标指路。转写时的正确落点是**内容层面的过渡句**，而非"详见第 X 章"式的结构指路。

| 卡片关系字段（原始） | ❌ 错误转写（结构暴露） | ✅ 正确转写（内容衔接） |
|---|---|---|
| "通用编排 Agent 与专业执行 Agent 是调度—被调度关系" | "专业执行 Agent 详见第二章第三节。" | "正是这一编排能力，为下游专业 Agent 的并行执行提供了调度基础——它们如何在编排指令下分工，是下一层要展开的问题。" |
| "本概念是上位概念 SSA 的语义扩展" | "SSA 的定义见前文第一章。" | "在 SSA'感知太空态势'的基础目标之上，本概念进一步要求对目标意图做出研判——这一层语义扩展正是后续分析的起点。" |

**要点**：关系字段的价值是让写作者知道"这一块知识和别处怎么连"，从而写出**内容上自然承接**的过渡；读者感知到的应是论证的流动，而不是"作者在报菜名式地指路"。坐标指路的收敛规则见 §7.2"前向引用坐标指路的分类型限额"。

## 7.1 写作标准

1. **证据驱动**：每个关键判断对应至少一个证据包（阶段 5.2 定义：claim_id + 来源），正文引用时使用上标编号 `^[N]^`（Markdown）或 `[N]`（Word），参考文献列表按 GB/T 7714-2015 格式排列（格式规范 §8）
2. **不确定性显式标注**：不把"可能/据称/尚未证实"包装成确定事实
3. **机制导向**：用"机制 / 链路 / 流程 / 约束 / 指标"表达，少用名词堆砌
4. **不写两张皮**：技术章节给业务含义，业务章节有技术支撑
5. **每章结构统一**：开头"本章结论" → 正文 → 末尾一节的收尾段落融入局限说明与章间过渡（不要求独立"对主论点的贡献"容器，见标准 5）

## 7.2 编号使用规范——哪些地方要编号，哪些不要

编号系统的技术实现（图表编号格式、章节自动编号、脚注、参考文献）已由 [`references/研究报告格式规范.md`](研究报告格式规范.md) 第四节统一规定，写作时不需要重新设计格式。本节规范的是**正文内容组织层面**的编号取舍——同一批材料，拆成编号列表还是写成连贯段落，直接决定条理性和可读性。

### 应当使用编号的场景

| 场景 | 编号方式 | 说明 |
|---|---|---|
| 机制/流程拆解（≥3 个有先后或依赖关系的步骤） | 阿拉伯数字 1. 2. 3. 或①②③ | 呼应标准 3"机制导向"：如"①边缘节点压缩回传→②知识图谱映射→③模型生成推荐→④人工确认下发"，编号体现步骤间的先后/依赖关系 |
| 启示/建议章节的每条建议 | "**建议 N：标题**" | 呼应标准 9，编号让读者能在结论/摘要中精确回指某一条建议 |
| 摘要的核心发现 | "**核心发现 N**：" | 呼应标准 12，3–7 条为宜，每条独立编号便于单独引用 |
| 红队风险清单条目 | R001、R002…（阶段 8 已定义） | 沿用 `red-team-checklist.md` 既有格式，不重复设计 |
| 图 / 表 / 公式 | 图 X-Y / 表 X-Y / 式(X-Y)（章号-序号，格式规范 4.2） | 写作阶段图号只在阶段 7 出图时分配，草稿中可先用占位描述，定稿前统一核对连续性 |

### 不应手动编号的场景

| 场景 | 原因 | 正确做法 |
|---|---|---|
| 章 / 节 / 小节标题 | 阶段 9 转换脚本按 `references/研究报告格式规范.md` 自动生成"第一章 / 1.1 / 1.1.1"；写作时若手动加编号（如标题写成"1. 导论"），会与自动编号叠加产生"第一章 第一章：导论"这类重复（详见 `references/md-to-docx-pitfalls.md` 问题 4） | 标题只写文字本身，不加任何数字/中文数字前缀，编号完全交给阶段 9 转换脚本 |
| 并列且无顺序/权重差异的要点 | 编号隐含"有先后"或"有优先级"，材料本身没有这层关系时会误导读者 | 用无序列表（`-` / `•`），不用阿拉伯数字 |
| 主张—证据—推理的论证性段落 | 标准 8 要求呈现完整推理链，拆成编号列表会把因果论证切碎成孤立要点，读者看不到"为什么" | 保持连贯段落叙述，不为了"显得有条理"而机械编号化 |

### 正文引用编号的规范

- 引用图表一律用具体编号（"如图 3-2 所示"），不用"下图""上表"这类依赖排版位置的说法——Word 排版分页后图表实际位置会变化，位置性指代会失效
- 引用建议/风险/发现编号时全文必须一致（如结论或附录中回指"建议 3"，需与该建议在原章节中的编号一致），阶段 9 整合时一并核对

### 前向引用坐标指路的分类型限额（对治"结构暴露"）

**问题**：正文里"见第 X 章""详见……节""与第 Y 节呼应""如前文限定"这类把文档骨架直接讲给读者的**坐标指路**，属"后台过程"的一种（读者要的是内容衔接，不是编辑部的目录结构），是 §7.2.3"结构暴露审计"要收敛的对象。但立项/技术报告确有"完整技术指标详见第三章"这类合理的前向引用需求，不能一刀切清零。

**规则**：

1. **默认不出现坐标指路**——章节之间的关联优先通过**内容层面的过渡句**实现（"正是在上述需求压力之下，下游专业 Agent 才需要……"），而非坐标（"专业 Agent 详见第二章第三节"）。参见 §7.0 之后"卡片关系字段→叙事衔接的转写指引"。
2. **确需前向引用时**，必须是"**内容承接 + 编号**"的复合形态（"完整的量化考核指标见第三章"），不能是纯坐标（"详见第三章"）。
3. **前向引用总数按报告类型分档限额**（`struct_template` 在阶段 4 大纲产出时即已确定，写作/审计 Agent 查表成本接近零）：

| struct_template | 前向引用限额 | 说明 |
|---|---|---|
| `brief`（快速简报） | **0 处**<!-- linkage-const:forward_ref_limit_brief:0 --> | 简报通篇 answer-first，短小自足，不应出现任何前向引用 |
| `research`（深度研究，默认） | **≤ 3 处**<!-- linkage-const:forward_ref_limit_research:3 --> | 机制导向叙事，少量"完整数据见后章"可接受 |
| `policy`（政策分析） | **≤ 3 处**<!-- linkage-const:forward_ref_limit_policy:3 --> | 比照 research |
| `proposal`（立项/可研） | **≤ 6 处**<!-- linkage-const:forward_ref_limit_proposal:6 --> | 技术指标/TRL/里程碑分散在多章，"详见第 X 章"是合理需要，限额放宽 |
| `tech-eval`（技术评估/选型） | **≤ 6 处**<!-- linkage-const:forward_ref_limit_tech_eval:6 --> | 评测方法与结论跨章，比照 proposal |

4. **图表引用不受本限额约束**——图/表用具体编号是 REF 域机制的硬要求（`writing-standards.md` 标准 6），"如图 3-2 所示"是规范做法而非坐标指路。本限额只针对"章/节"级的文字坐标指路。

> **审计口径**：§7.2.3"结构暴露审计"正则命中后，审计 Agent 先剔除图表引用与已做内容承接的复合引用，再数纯坐标指路 + 超限的前向引用条数，超出本表限额 → 判该维度 block（改为内容衔接或删减）。

## 7.2.2 分章文件中的标题书写规则（与 md→docx 转换器的合约）

> **标题文本权威来源**：Writer 分章文件中各级标题的**纯文字文本只能来自** `outline.md` 的 YAML front matter 中的 `section_title` / `subsection_title` 字段。YAML 已分离 `section_no`（编号元数据）和 `section_title`（标题文本）——编号是元数据，不是标题文本的一部分。**Writer 必须从 YAML `section_title` 取纯文字标题**，不得从 Markdown 正文 heading 的编号前缀部分提取、不得将编号写入分章文件标题。orchestrator 在注入 Writer prompt 时须从 YAML `section_title` 字段提取标题文本，而非从 Markdown heading 解析。

**Writer 分章文件起始规范**：每个分章文件以 `> **本章结论**：...` blockquote 起始（严格遵循 `references/writer-template.md` 定义的强制输出骨架），随后以分隔线 `---` 过渡。正文节从 H3（`### 节标题`）开始，按大纲顺序依次展开。分章文件中**不写 H2**——章容器（`## 第 X 章：<chapter_title>`）由 `finalizer_agent` 在阶段 9 合并时按 `outline.md` 的 YAML 结构清单统一插入。完整骨架见 `references/writer-template.md` 第一节。

**核心原则：分章文件中的标题只写纯文字，不加任何数字前缀或中文数字编号。所有编号（"第一章/1.1/1.1.1"）完全由阶段9转换脚本自动生成。**

| 层级 | Markdown | 正确示例 | 错误示例 | 说明 |
|------|----------|---------|---------|------|
| **前言/导论** | `#` (H1) | `# 前言/导论` | `# 0. 前言` | 全文唯一H1，也是转换器识别的MAIN_TITLE |
| **前言各节** | `##` (H2) | `## 问题提出与研究背景` | `## 0.1 问题提出` | 不加"0.1/0.2"编号，转换器识别为前置件不编号 |
| **正文章容器** | `##` (H2) | `## 第一章 军事需求与现状分析` | `## 军事需求分析`（缺章容器，见下方说明） | 与 `outline.md` 的章级条目一一对应，**不由分章写作者写**——由 `finalizer_agent` 在阶段9合并分章文件前插入（`stage-9-finalize.md` §9.1.x） |
| **正文各节** | `###` (H3) | `### 军事需求分析` | `### 1.1 非合作目标异动` | 分章写作者**只写到本级**，H3不加"1.1/1.2"编号；一个分章文件通常对应大纲中的一个"节"而非一整个"章" |
| **正文各小节** | `####` (H4) | `#### 轨道残差异常快速检测` | `#### 1.1.1 轨道残差` | H4不加"1.1.1"编号 |
| **附录** | `##` (H2) | `## 附录A：事实核验台账摘要` | — | H2，转换器识别APPENDIX |

> **2026-08-03 变更**：Writer 不再输出 `## 本章结论` H2，改为 blockquote。合并阶段**不再需要标题下沉**——Writer 产出层级直接就是合并后正确层级。分章文件中的第一个 heading 是 `### 正文节标题`，对应合并后的 SECTION 层级。
>
> | 分章草稿 | 合并后 | docx 样式 |
> |---|---|---|
> | （不写章容器） | `##` 第 X 章：… | `Heading 1` |
> | `> **本章结论**：...` (blockquote) | `> **本章结论**：...` (blockquote) | `Normal`（非 heading） |
> | `### 正文节标题` | `### 正文节标题` | `Heading 2` |
> | `#### 正文小节标题` | `#### 正文小节标题` | `Heading 3` |

**为什么正文不使用 H1？** 转换器将第一个 H1 视为主标题（MAIN_TITLE），后续 H1 全部降级为 CHAPTER 处理。如果正文各章使用 H1（如`# 第一章 xxx`），将触发 W-HDR-03 警告，且可能导致编号错乱。正文的"章"层级统一使用 H2 可以避免这个问题。

**为什么"正文章容器"行的旧错误示例`## 军事需求分析`是错误的（历史教训，勿抄回）**：早期版本把这一行的"正确示例"写成了单层 H2（`## 军事需求分析`），没有说明它是"章容器"、也没有展示与 H3"节标题"的两级嵌套关系。写作 Agent 逐字仿照这个单层示例，导致 20 个分章草稿普遍以 H3 起手、全篇缺少与 `outline.md` 对应的 H2"第一章～第五章"容器标题，合并后标题编号退化为扁平的"0.1～0.57"格式（详见 `references/writing-process-pitfalls.md` 问题1）。**教训**：本表的"正确示例"必须同时体现层级关系（H2 章容器 + H3 节标题），不能只给单层孤例。

**分文件写作时的注意事项**：每个分章文件从 `> **本章结论**：...` blockquote 开始（严格遵循 `references/writer-template.md` 的强制输出骨架），随后是正文 H3 节标题（`### 节标题`，纯文字，不加编号）。**不写本章所属的 H2 章容器标题**——章容器标题由 `finalizer_agent` 在阶段9合并阶段按 `outline.md` 的 YAML `structure.bodymatter` 中的 `chapter_title` 统一插入（同属一章的多个分章文件共享同一个插入的 H2 `## 第 X 章：<chapter_title>`）。合并为 `final-report.md` 后，所有 H2/H3 被转换器按顺序正确编号。不要在分章文件中写 `# 第X章` 这样的 H1 标题——合并后会触发多个主线 H1 的冲突。

## 7.2.3 每章完成后的即时自查（不通过不解锁下一章）

每章草稿完成后，必须按以下清单逐项自查并打勾。这是阶段7质量门槛的**前置执行机制**——不依赖阶段7全部完成后才检查，而是在每一章的写作循环末尾即时触发。

- [ ] **本章结论段落**存在且为3-5句话概括（非一句话敷衍）
- [ ] **局限说明**：本章最后一个正文节的收尾段落是否含至少1句可识别的局限说明，不要求独立"对主论点的贡献"容器（写作标准 11）
- [ ] **推理密度检查**：随机抽查3段连续文字，每段包含实质性推理（主张/事实/Warranty三角），非纯叙述或纯事实罗列（写作标准 7）
- [ ] **强表述检查**：全文搜索"首次/最大/完全/秒级/决定性/全自动"，每条均有A/B级证据（写作禁区第4条）

## 7.3 写作顺序

按大纲顺序逐章推进。**每章的写作循环采用"先叙事大纲后填证据"的顺序**——先立论点骨架（读者视角的判断），再回填卡片里的精炼事实做支撑。这是本 skill 写作方法的核心杠杆：当写作从"论点骨架"出发时，卡片字段自然退到"被查用的素材库"位置，不可能把整张卡片翻译进一个已由论点驱动的段落，从源头消除"逐卡誊抄"（对标 Minto 金字塔"先立骨、后挂肉"与折叠脚手架原则）。

```text
先写本节叙事大纲(论点骨架) → 回填证据(从卡片取事实支撑) → 按标准0查后台外泄 → 确认本章架构图已就位 → 嵌入架构图 → 如需数据图表则orchestrator调data_chart_agent产出 → Writer嵌入数据图表 → 检查证据源/台账 → 回填卡片使用记录 → 进入下一章
```

具体步骤：

1. **先写本节叙事大纲（论点骨架）**：只看大纲条目的"本节要论证什么 + 论证路径"，以及卡片新增的"一句话论点 / 机制小结 / 采用定义"消化字段（见 `stage-5-cards.md` §5.3），写出本节 3-6 句话的**论点骨架**——每句是一个判断，按结论先行排列。**此时不看卡片的时间线/关键数据/证据包等事实字段细节**，避免一上来就被字段牵着走。
   > **⚠ 论点骨架的来源约束（防"先射箭后画靶"）**：论点骨架**只能来自**两处——(a) 大纲条目的论证路径（已由 `outline_architect_agent` 基于核验过的事实产出）；(b) 卡片的"一句话论点/机制小结/采用定义"消化字段（这些字段本身已绑定证据包）。**不得凭空立论、不得先编一个"漂亮结论"再去卡片里找证据凑**。骨架里的每个判断都应能追溯到上述某一来源。
2. **回填证据**：为骨架的每个判断，从卡片的事实字段（数字、时间线、来源）中**取用**支撑，嵌入叙述、补脚注。
   > **无证据支撑的判断必须降级或删除**：若回填时发现某个判断在卡片/台账里找不到证据支撑，说明它是凭空推断——按现有证据密度门槛（标准 7）降级表述（加限定词）或直接删除，**不得为了保留漂亮结论而放宽证据要求**。这一步是对步骤 1 论点骨架的证据校验闸门。
3. **按 `writing-standards.md` 标准 0 检查后台外泄**：骨架 + 证据成文后，逐句检查是否混入了证据分级、来源取舍、核验状态、claim_id、方法论自评等后台内容，命中即改写为成品判断 + 脚注或删除（呼应 §7.0 铁律 4、§7.2.3 后台外泄审计）。
4. **确认本章所需架构图已就位**：检查 `research/figures/` 中是否存在本章规划的核心架构图（总览图/架构图/流程图）的 PNG 文件。架构图由 `architecture_chart_agent`（Sonnet）在阶段 6 产出，此时应已就位。**如有缺失，Writer 不得自行绘制架构图——上报 orchestrator，由 orchestrator 判断：调用 `architecture_chart_agent` 补图 / 降级为文字描述 / 记录到质量门槛备注。**
5. **嵌入架构图**：将架构图以 `![图X-Y 标题](research/figures/图X-Y-描述.png)` 格式嵌入 Markdown 正文对应位置。确保首次引用在图之前（写作标准 6）。每个图注需说明图的逻辑或来源。

### 图片引用——使用速查表（v3 新增）

Writer 在嵌入图片时，**不得自行构造图片文件名**。必须使用 orchestrator 注入的
"本章图片引用速查表"（从 `research/figures/figure-path-map.json` 中提取当前章条目）。

速查表中每条含 `markdown_ref` 字段——完整的 `![图X-Y 标题](figures/文件名.drawio.png)` 语法。
Writer 逐字复制 `markdown_ref` 到正文中，不做任何修改。

违反此规则的常见模式（v3 起视为 FATAL）：
- 将文件名中的中英文连字符改写（如 `SCIF-Agent` → `SCIFAgent`）
- 修改扩展名（`.drawio.png` → `.drawio` 或 `.png`）
- 不使用速查表提供的精确文件名

5.5 **产出本章规划表格**（表格是 Markdown 正文的一部分，Writer 自行编制，不走独立 Agent）：
   a. 从大纲条目中确认本章的表格规划（如有 `figures_manifest.tables`，按 `table_no` + `title` 产出；否则按大纲 Markdown 正文的"图表规划"行产出）
   b. 表格题注规范：使用 `**表X-Y：标题**` 加粗格式（作为 Markdown 正文的一部分），位于表格上方
   c. 数据来源行：每个表格的题注下方或表末附加 `> 数据来源：<机构，报告/数据库名称，年份>` 引用块
   d. 交叉引用编号：表格编号格式为 `表X-Y`（X=章号，Y=章内表序号），与 `figures_manifest.tables.table_no` 一致（如存在）。正文中引用表格统一用"如表X-Y所示"
   e. 首次引用在表格之前：正文中首次提到该表格时，应在表格出现之前引用（写作标准 6）
   f. 表格规范详见 `writing-standards.md` 标准 21"表格写作规范"

   b. Writer 将出图需求上报 orchestrator（通过草稿中的标注或直接沟通）

   d. `data_chart_agent` 产出 PNG 到 `research/figures/`，回报 orchestrator
   e. Orchestrator 将 PNG 文件路径回报 Writer

   > ~~a. 加载报告图表样式模板：`plt.style.use('design/chart-quality-constraints/matplotlib-report-style.mplstyle')`~~
   > ~~b. 选择图表类型——对照决策表，禁止 3D 和 >5 扇区饼图~~

7. 检查该章的证据源是否都标注了可信度等级
8. 检查是否出现了阶段 3 台账中标记为"不入正文"的主张
9. 检查首次性/最强级表述是否都有 A/B 级证据

**为什么用这个顺序（论点先行 + 图表随写）**：论点骨架先行让卡片退回"素材库"定位，直接对治"卡片内容太精炼、直接转写让读者困惑"——先有读者能懂的论点，再填精炼事实做支撑，精炼就不再是问题。而图表随每章写作产出，是因为写作时脑中有数据、有上下文，此时出图最自然，不会出现"图表是对的但文字用不上"或"文字需要一张图但之前没做"的脱节。

## 7.4 报告内容质量标准——不只是"不出错"，还要"写得好"

过程严谨保证下限，内容质量决定上限。以下 6 条标准（标准 7-12，对应 `writing-standards.md` 中的完整编号体系）用于每章写作后的自查，也用于阶段 8 红队审查时的内容维度打分。编号对照见 `writing-standards.md` 末尾"标准编号体系对照"表。

### 标准 7：推理密度

**每段有推理，非每段有引用。** 每个自然段应包含实质性的推理内容——事实、分析、逻辑推演或综合判断。连续多段纯叙述而无分析或推理的段落，通常是写作者在"填充字数"而非"推进论证"。

自查方法：
1. 逐段问自己：这段话对论证的推进是什么？如果答案是"提供了背景信息"或"过渡"，确认它是必要的；如果答案是"没有实质推进"，删除或合并。
2. 检查每段是否包含以下至少一项：(a) 一个由证据支撑的判断；(b) 一段从事实到结论的推理（Warranty）；(c) 一个需要向读者诚实说明的不确定性。
3. 如果一段只有"陈述事实"而没有"分析事实"，检查这段事实是否已经在推理段中使用——如果是，它应该合并入推理段而非独立成段。

### 标准 8：主张—事实—Warranty 三角

**每个关键主张的论证呈现完整三角结构：主张（我们要论证什么）→ 事实（支持主张的具体证据）→ Warranty（为什么这些事实支持这个主张，逻辑链条是什么）。Warranty 不是复述事实也不是重复主张——它是揭示事实和主张之间逻辑关系的桥梁。**

❌ 只有主张无证据：
> 东南亚新能源汽车市场正处于爆发前夜。

✅ 完整三角：
> **主张**：东南亚新能源汽车市场正进入快速增长期。
> **证据**：据泰国工业联合会 2025 年报，泰国 2025 年 BEV 销量同比增长 240%，充电桩数量从 2024 年的 2,800 个增至 2025 年的 9,000+ 个。
> **推理**：销量 3 倍增长 + 基础设施同步扩张 → 不只是政策补贴的短期效应，而是供需双轮驱动的结构性增长。

### 标准 9：建议的可操作性

**启示/建议章节的每一条必须回答：谁来做？做什么？在什么条件下？用什么资源？预期效果如何衡量？**

❌ 空泛建议：
> 企业应加强本地化布局。

✅ 可操作建议：
> **谁**：海外事业部战略规划组。
> **做什么**：2026 Q4 前完成泰国 Rayong 的 KD 工厂选址（优先考察 WHA 工业区，因比亚迪/长城已入驻形成配套集群）。
> **资源**：初期投入约 2-3 亿泰铢（~600 万美元），需董事会批准海外投资额度。
> **效果指标**：工厂投产后 12 个月内本地化率 > 40%，享受泰国 EV 3.5 计划全额税收优惠。

### 标准 10：量化优先

**能用数字就不用形容词。** 优先用数量、比例、时间、金额、排名来表达。

| 弱表述 | 强表述 |
|---|---|
| "大幅增长" | "同比增长 240%" |
| "显著缩短" | "从 30 分钟缩短至 2 分钟" |
| "成本较高" | "TCO 比方案 B 高约 35%（5 年期）" |
| "很多企业已布局" | "截至 2026Q1，至少 8 家中国 Tier-1 零部件企业在泰国设厂" |

### 标准 11：承认边界

**每章结尾（最后一个正文小节的收尾段落）必须包含至少 1 句对本章分析局限的说明，不要求独立成段或字面标签。**

示例：
> 本章分析基于截至 2026 年 5 月的公开资料。三地试点政策仍在快速演变中（成都于 2026 年 4 月发布了新版空域管理细则，因截稿时间未能纳入详细分析）。此外，由于无法获得三地政府内部决策文件，制度逻辑的分析主要基于公开政策文本和二手访谈，存在推断成分。

### 标准 12：摘要的可独立阅读性

**摘要不是目录的散文版，而是报告的浓缩版。** 读者只读摘要也应该能理解：背景、问题、方法、核心发现（3-7 条）、主要建议、关键约束。

每个核心发现用 **加粗一句话** 开头，后面跟 2-3 句支撑。

### 标准 18：章节与节间过渡

章间过渡（≥2 句，本章小结 + 内容层面引出下一章，融入最后一节收尾段落，不强制引用块字面标签）+ 节间过渡（≥1 句，内容承接而非坐标指路）。详见 `writing-standards.md` 标准 18。

### 标准 19：读者层次校准

缩写首次出现必须展开（全称 + 中文释义），关键概念首次出现给 1 句解释。默认读者画像为"对该领域有基本素养但不掌握项目特定细节的专业人士"。详见 `writing-standards.md` 标准 19。

### 标准 20：段落长度与信息密度

段落理想区间 150-400 字（中文），>600 字必须拆分。每 300 字至少 1 个数据点支撑。详见 `writing-standards.md` 标准 20。

## 7.5 写作禁区

- 未完成事实核验的主张直接写入正文
- 把 D 级来源当作结论使用
- 把领域核心概念写成泛泛的科普（必须落到机制层面）
- 使用"完全""首次""秒级""决定性"等强表述而无 A/B 级证据
- 只堆材料不做机制提炼，或只谈概念不给案例/数据/图表
- 写"据外媒报道""有消息称"等空泛来源——必须在参考文献列表中给出完整来源信息（GB/T 7714-2015 格式），正文中通过上标编号 `[N]` 引用

> **dataviz 颜色校验（可选）**：如果项目环境中 `dataviz` skill 可用，在阶段 7 首张数据图表产出后触发 `/dataviz` 进行颜色合规校验。若不可用，执行 `python scripts/chart_checks.py --colors --figures-dir research/figures/` 作为等价替代。校验结果不阻塞写作流程，仅记录到阶段 7 质量门槛备注中。
