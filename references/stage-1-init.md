## 1.0 模型能力档检测与配置（强制执行，先于参数推断）

**这是阶段 1 的第一个强制步骤——先知道跑在什么模型上，再做参数推断和协同模式选择。不可跳过。**

### 为什么必须先做

`model-profile.json` 声明的能力档（tier A/B/C）影响后续所有阶段的行为参数——红线条数限制、输出信封 nonce、填空骨架模式、phase_a_mode、协同模式的二维决策。如果跳过此步骤直接用默认假设（=Claude tier A），在 DeepSeek/GLM/Qwen 等非 Claude 模型上运行时会出现：

- 协同模式与模型实际委派能力不匹配（agent_delegation 假设错误）
- 红线预算错误（Tier A=不限 vs Tier B=5条 vs Tier C=保守档）
- 输出信封 nonce 不一致（Tier A 不要求但 Tier B/C 强制 → 噪声检测误判）
- 填空骨架模式偏移（Tier A=off 时 Writer 拿不到结构化段落骨架）

### 执行流程

**步骤 1：自动探测并配置**

```bash
python scripts/model_profile.py --model auto
```

脚本从环境变量（`CLAUDE_CODE_MODEL` / `LLM_MODEL`）自动探测当前模型标识符，匹配内置映射表，生成 `.gitignore` 保护的 `model-profile.local.json`。若该文件已存在则跳过（不覆盖已有配置）。

**步骤 2：若自动探测失败（exit code ≠ 0）→ 显式传入模型名**

从会话上下文（如系统提示中的 `You are powered by the model deepseek-v4-pro-guan-cc`）获取当前模型标识符，显式传入：

```bash
python scripts/model_profile.py --model "<实际模型名>"
```

**步骤 3：加载生效配置并验证**

```bash
python scripts/model_profile.py --json
```

解析 JSON 输出，提取以下关键字段并记录到阶段台账：

| 字段 | 来源 | 用途 |
|------|------|------|
| `capability_tier` | 文件声明 | 决定 Tier A/B/C 行为参数 |
| `host.agent_delegation` | 文件声明 | 若为 `false` → 强制降级为单 Agent 极速档 |
| `limits.max_output_tokens` | 文件声明 | 派生 `phase_a_mode`（<16K→confirm，≥16K→free） |
| `phase_a_mode` | 派生量 | 审计 Agent Phase A 书写形态 |
| `policy.hard_rule_budget` | 文件声明 | Writer/Auditor 单次调用的红线数量上限 |
| `policy.envelope_nonce` | 文件声明 | 子 Agent 输出是否强制带 nonce |
| `policy.template_fill_mode` | 文件声明 | Writer 是否启用填空骨架 |
| `_source` | 运行时标记 | 区分"文件正常加载"/"fallback 兜底" |

**步骤 4：能力档 × 协同模式交叉校验**

将步骤 3 加载的 `capability_tier` 与 1.1 参数推断后得出的协同模式（完整/分层/极速）做交叉校验。调用 `resolve_collaboration_mode()` 的硬规则逻辑（orchestrator 端手动执行，不调脚本）：

- `agent_delegation == false` → 强制降级为"单 Agent 极速"，标注原因
- `Tier C × 完整多 Agent` → 强制降级为"分层多 Agent"，写台账
- `Tier B × 完整多 Agent` → ⚠️ 允许但标注"未经实测"风险
- 其余组合 → 正交，不互相覆盖

**步骤 5：在参数确认表中展示能力档信息**

将模型能力档的**关键约束摘要**作为参数确认表的一个信息行展示（不是让用户确认，而是告知用户当前运行环境）：

```
| 运行环境 | DeepSeek V4 / Tier B / Agent委派=是 / max_tokens=380K | ℹ️ |
```

> ℹ️ 表示信息行，非确认项。用户不需要对此做选择——这是 orchestrator 自我感知的结果。

### 输出要求

本步骤完成后，orchestrator 在进入 1.1 之前必须在日志/台账中记录：

1. **生效的能力档**（tier A/B/C + `_source` 来源标记）
2. **协同模式交叉校验结果**（原始请求档位 → 实际生效档位，如有降级则记录降级原因）
3. **Tier B × 完整档风险标记**（如适用）

### 兜底行为速查

| 情形 | 行为 |
|------|------|
| `model-profile.local.json` 已存在 | 跳过自动配置，直接加载生效配置 |
| 自动探测 + 显式传入均失败 | fallback 到 tier A（=Claude 行为），写台账警告 |
| 文件存在但 JSON 解析/schema 校验失败 | 降级到 tier C，写台账 + 显式告警 |
| 文件存在且合法 | 按声明的 tier 运行 |

> **与本步骤相关的代码与文档**：`scripts/model_profile.py`（加载器/自动配置器）、`references/multiagent-orchestration.md` §7.5（二维决策矩阵）、`SKILL.md` §模型能力档（总纲）。

## 1.1 智能推断 + 快速确认

从用户请求中提取已知信息，对未提供参数填入默认值。**一次性展示全部推断结果，只标出需要用户纠正的关键项。**

### 报告类型自动识别

从用户请求中识别报告类型，自动匹配模板结构。不同类型的报告有不同的结构需求——立项报告需要技术指标量化表和创新点归纳，政策分析需要条文解读框架，技术评估需要评测方法论。

| 报告类型 | 信号词 | 默认模板 | 特殊模块 | 协同模式 |
|---------|--------|---------|---------|---------|
| **立项报告/论证报告** | "立项"、"论证"、"项目建议书"、"可行性"、"申报"、"申请书" | 必选骨架 + 立项专用可选模块集 | 技术指标与考核方式、创新点归纳、TRL评估、进度里程碑、研究基础 | **完整多 Agent** |
| **深度研究报告**（默认） | "深度分析"、"研究报告"、"白皮书"、"行业分析" | 当前必选骨架 + 当前可选模块池 | 无特殊新增 | **分层多 Agent**（默认） |
| **政策分析报告** | "政策"、"法规"、"条文"、"治理" | 必选骨架 + 政策专用可选模块集 | 条文解读方法、利益相关方矩阵、政策影响评估框架 | 分层多 Agent（可按篇幅升/降） |
| **技术评估报告** | "技术评估"、"选型"、"对比"、"评测" | 必选骨架 + 技术专用可选模块集 | 评测方法论、基准测试设计 | 分层多 Agent（可按篇幅升/降） |
| **快速简报** | "简报"、"快速"、"概览"、"brief" | 极速模式压缩模板 | 无特殊模块——自动触发极速模式 | **单 Agent 极速** |

若用户未使用任何信号词，默认归类为"深度研究报告"。

> **协同模式列**（v4 §7.3 / v5 #11）：报告类型识别后，`struct_template` 与协同模式一并派生——proposal→完整多 Agent，research（默认）→分层多 Agent，brief→单 Agent 极速，policy/tech-eval→分层多 Agent（可按篇幅升降）。协同模式的完整触发阈值见 SKILL.md"三档协同模式"表。用户说"继续"即用推断的协同模式启动，不新增交互负担。

### 默认值规则

| 参数 | 默认值 | 覆盖条件 |
|------|--------|---------|
| 题名 | 从请求中提取关键词生成 | 用户明确指定标题 |
| 定位与受众 | 行业决策者 / 投资人 | 用户提到"学术""政府""内部"等信号词时替换 |
| 核心问题 | 题名的疑问句形式（如"XX 的现状、竞争格局与趋势是什么"） | 用户明确提出问题 |
| 规模 | 30–50 页（标准深度） | 用户说"简报""快速"→15页；"深度""全面"→60页+ |
| 交付期限 | 无紧迫期限 | 用户给出具体日期 |
| 已有素材 | 无，完全从公开资料收集 | 用户提供文件/链接 |
| 领域特殊要求 | 无特殊要求 | 用户说明禁忌/偏好/框架 |
| 分析框架 | 自动匹配 2 个最相关维度（见 1.3） | 用户指定框架 |
| 研究方法 | 自动匹配 1–2 个最相关方法（见 1.3 附表） | 主题需要德尔菲法/专家访谈法等依赖用户资源的方法时 |

### 展示格式

收到用户请求后，先执行 1.0 模型检测，然后**一次性展示**下表（运行环境行来自 1.0 检测结果，不单独展示）：

```
📋 参数确认（直接回复"继续"用默认值启动，或指出需修改的项）

| 参数 | 推断值 | |
|------|--------|---|
| 运行环境 | <模型名> / Tier <A/B/C> / Agent委派=<是/否> / max_tokens=<N> | ℹ️ |
| 题名 | 《XX 深度分析报告》 | ✅ |
| 受众 | 行业决策者 | ✅ |
| 研究方法 | 文献研究法 + 比较研究法 | ✅ |
| 核心问题 | XX 的现状、格局与趋势是什么？ | ✅ |
| 规模 | 30–50 页 | ✅ |
| 协同模式 | 分层多 Agent（核心章写作+独立审计对抗） | ⚠️ 简报可选"单 Agent 极速" |
| 期限 | 无紧迫期限 | ⚠️ 如有期限请告知 |

```

> ℹ️ = 信息行（orchestrator 自我感知结果，用户无需确认）。若有降级（如"Tier B × 完整多 Agent 未经实测"），在此行后追加降级提示。

> **协同模式行**（v4 §7.3 / v5 #23）：协同模式由报告类型派生（见上方类型识别表的"协同模式"列 + SKILL.md"三档协同模式"表的完整阈值），在阶段 1.1 最早期就确定并对用户可见。用户说"继续"即用推断的协同模式启动——不新增用户交互负担。触发阈值：立项/≥40页/核心章≥3 → 完整多 Agent；研究报告 30-50 页/核心章 2-3 → 分层多 Agent（默认）；简报/<15页/≤2章/用户说"简报/快速" → 单 Agent 极速。

> **规则**：运行环境行为 ℹ️ 信息行（不参与计数），其余 7 项中 ≤ 2 项标 ⚠️。标 ⚠️ 的项是"不说也能继续但说了更好"——不是阻塞条件。若有降级（1.0 步骤 4 交叉校验结果），降级提示紧跟在运行环境行后展示。

### 快速启动

用户回复"继续""go""开始"或任何等同信号 → 立即以默认参数进入阶段 1.2（建立工作目录）。只有在用户主动纠正某个参数时才调整。

### 研究范围确认——仅当用户提供了素材时触发

**触发条件**：用户在发起请求时随附了文件/文件夹/URL 列表（即"已有素材"不为默认值"无"）。未提供素材时跳过本步骤，直接走 1.1 常规确认流程进入阶段 2（此时阶段 2.0 天然会执行完整搜集）。

**为什么必须单独停下来问**：用户提供素材，不代表用户希望"仅基于这些素材写作"——素材可能只是用户手头恰好有的参考资料，报告仍需扩展搜集来补全证据链和独立信源（尤其影响阶段 3 事实核验：如果全部来源都来自用户单方提供，核验台账找不到独立信源交叉验证）。这是一个决定报告可信度基础和工作量的范围决策，不能被默认值或"继续"一并带过。

🛑 **STOP**：检测到素材后，必须先用 AskUserQuestion 单独确认研究范围，不接受笼统的"继续/go/开始"越过此项：

```
📎 检测到您提供了 N 份素材。请明确研究范围：

A. 仅基于您提供的素材（针对性分析报告）
   → 不额外搜集外部资料，核验和分析范围限定在素材内
B. 素材 + 扩展搜集（综合研究报告，推荐）
   → 以您的素材为基础，按阶段 2.0 优先级补充外部来源，
     用于交叉验证和填补素材未覆盖的部分
```

用户选 A → 阶段 2.0 标记为"跳过扩展搜集"，直接进入 2.2 文本抽取，但阶段 3 事实核验时对无法交叉验证的主张标注"仅单一来源（用户提供），未做外部核验"。
用户选 B（或未明确偏好、只说"帮我参考一下"这类模糊表述）→ 阶段 2.0 正常执行完整搜集流程，用户素材与外部搜集结果合并登记到来源索引。

本确认与 1.1 参数确认可以合并展示（同一轮对话内），但**必须等到用户明确二选一后才能进入阶段 1.2**——不因用户只回复"继续"而默认选择 B。

## 1.2 建立工作目录与工具路径配置

在项目根目录创建 `research/` 目录骨架。目录名约定以 `references/stage-5-cards.md` §5.0 为唯一权威来源，如需改名只改该处和此处，不可在各 Agent prompt 中单独修改。

```text
research/
  sources/          # 来源元数据索引（不移动原始文件）
  extracted/        # 抽取的文本
  claims/           # 事实核验台账
  notes/
    case-cards/     # 案例卡片
    tech-cards/     # 技术/主题卡片
    architecture-cards/  # 架构卡片
    theory-cards/   # 理论/概念卡片
    card-index.csv  # 卡片索引：登记每张卡片的类型/对应章节/关联证据包/是否已被阶段7引用
  figures/          # 图表（草稿 + 终稿）
  drafts/           # 分章草稿
```

**工具路径配置**：外部工具的脚本路径集中存放在 [`references/tool-paths.json`](tool-paths.json) 中。首次使用时，用户需将其中 `absolute_path` 字段填写为实际的绝对路径（安装路径），或留空表示该工具未安装/暂不使用。

配置方式（任选其一）：
- **手动编辑**：直接修改 `references/tool-paths.json` 中的 `absolute_path` 字段
- **自动检测**：skill 执行时尝试 `where`/`which` 查找工具路径，将结果写入 `tool-paths.json`

配置完成后，阶段 2/6 中调用外部工具的命令将自动读取 `tool-paths.json` 中的路径，无需在 SKILL.md 中硬编码。

> **示例**：如果 MinerU 安装在 `D:\tools\mineru\scripts\mineru_parse.py`，则将 `"absolute_path": ""` 改为 `"absolute_path": "D:\\\\tools\\\\mineru\\\\scripts\\\\mineru_parse.py"`（注意 JSON 中转义反斜杠）。

**封面文件独立于正文 Markdown**：后续阶段如需修改封面信息（如标题调整、版本号更新），只需编辑 `research/cover.md` 这一文件，不影响正文草稿。转换器通过 `--cover research/cover.md` 参数读取封面字段，优先级高于正文 YAML frontmatter。封面未生成的默认字段沿用 1.1 确认表中的推断值，用户不确认不阻塞后续阶段。

## 1.3 确认分析框架与研究方法

根据报告主题，与用户确认适用的分析框架。通用框架包括：

- **闭环机制**：主题领域的"输入 → 处理 → 输出 → 反馈"闭环是什么？
- **架构分层**：主题可以从哪些架构视角拆解？（如：业务架构 / 技术架构 / 数据架构 / 组织架构 / 治理架构）
- **需求/变化分层**：该领域的变化速度可以分几层？（如：快速响应 / 中期演进 / 长期升级）
- **风险维度**：该领域的主要风险类型有哪些？

> **领域适配**：主题明确时自动匹配 2 个最相关维度（见领域适配指南），不需要逐项询问。主题模糊时默认选"架构分层 + 闭环机制"。

**研究方法**：分析框架回答"怎么切内容"，研究方法回答"怎么收集证据、组织论证"。两者互相独立，同一报告可以任意组合。按主题特点自动匹配 1–2 个方法，写入 1.1 确认表：

| 方法 | 适用场景 | 可行性 | 默认触发条件 |
|---|---|---|---|
| 文献研究法 | 所有报告的基线方法 | 高——web-search-skill + paper-search 直接支撑 | 始终包含 |
| 比较研究法 | 竞争格局/跨国/跨企业/跨方案对比类报告 | 高——多源检索天然支持横向对比 | 主题含"对比""格局""竞争"等信号词 |
| 案例研究法 | 机制拆解、单/多案例深挖类报告 | 高——对应阶段 5 案例卡片，天然契合 | 主题含"案例""机制""怎么做到的"等信号词 |
| 内容分析法 | 政策文本/法规条款/舆情类报告 | 高——MinerU 精准解析 + 结构化抽取支撑 | 主题含"政策""法规""条款"等信号词 |
| 情景分析法 | 趋势预测、战略前瞻类报告 | 中——AI 可基于证据推演情景，但情景假设合理性需人工把关 | 主题含"预测""展望""情景""2030"等未来性信号词 |
| 德尔菲法 / 专家访谈法 | 需要一手专家判断的报告 | 低——依赖用户提供真实专家资源，本 skill 工具链无法独立完成 | 用户明确要求，或主题信息高度稀缺、公开资料无法支撑结论 |

> **默认组合**：无特殊信号词时，默认"文献研究法 + 比较研究法"。命中德尔菲法/专家访谈法触发条件时，在 1.1 确认表对应行标 ⚠️，并向用户说明"需要您提供可联系的专家渠道，否则将降级为文献研究法"。

🔴 CHECKPOINT · STOP：用户回复"继续/开始/go"或纠正完参数后，立即进入阶段 2。即使个别 ⚠️ 项未回复也不阻塞——在后续阶段发现信息不足时再补充。
