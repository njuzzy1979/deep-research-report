# 写作/协同过程踩坑记录——根因链分析

本文档与 `references/md-to-docx-pitfalls.md` 是互补关系，边界如下：

- **`md-to-docx-pitfalls.md`**：记录 md→docx **转换器代码层面**"哪里的代码错了、改了哪段代码"——面向要维护/调试转换脚本的人。
- **本文档（`writing-process-pitfalls.md`）**：记录同一批问题在**写作/多 Agent 协同流程层面**"为什么会发生、流程设计上哪个环节失守"——面向要设计/审查 skill 内 Agent 契约、参考文档、质量门槛的人。同一个故障现象，两份文档回答的是不同层级的"为什么"：转换器文档回答"代码为什么处理不了"，本文档回答"这批坏数据当初为什么会被写作 Agent 产出"。

阅读顺序建议：先读本文档理解"上游为什么会产生这类问题"，再读 `md-to-docx-pitfalls.md` 理解"下游转换器如何兜底/为什么兜底也失效"。两者共同构成"预防 + 检测 + 修复"的完整闭环——本文档侧重预防（如何从源头避免同类问题在下一个项目重演）。

## 问题1：章节结构扁平化（H2 章容器缺失）

**症状**：20 个分章草稿普遍以 H3 起手，全篇缺少与 `outline.md` 对应的 H2"第一章～第五章"容器标题。合并后，md→docx 转换器按 Markdown 标题层级自动生成编号，由于最高层级标题是 H3 而非 H2，编号退化为扁平的"0.1～0.57"格式，完全丢失"章"这一层级的语义分组。

**根因（流程层面的双重失效叠加）**：
1. **规范文档示例误导**：`stage-7-writing.md` §7.2.2 早期版本的"正文各章"行只给出单层 H2 示例（`## 军事需求分析`），没有说明这是"章容器"、也没有展示它与 H3"节标题"之间的两级嵌套关系。写作 Agent（`chapter_writer_agent`）阅读该表时，把这个孤立的单层示例当作"正文标题应该长什么样"的唯一参照，逐字仿照，于是普遍从 H3（甚至更深层级）起手，从未产出过 H2 章容器。
2. **验证工具的空真值陷阱同时失效**：即便写作阶段产出了结构缺陷草稿，理论上门3（`gate3.py`）的章节连续性校验应当在转换阶段拦截并报错。但该校验逻辑存在"空真值陷阱"——`all(x is None for x in [])` 对空列表返回 `True`，导致"章节列表整体为空（结构性缺失）"与"章节列表非空但都没有手动编号（正常场景）"被同一段代码误判为同一种"跳过检查"的情况。两道本应独立生效的防线（写作阶段的规范约束、转换阶段的自动校验）恰好在同一个故障场景下同时失效，问题一路带到最终产出物才被人工发现。

**修复**：
- 写作规范层：`stage-7-writing.md` §7.2.2 表格新增独立的"正文章容器"行，展示正确的两级嵌套示例（H2 章容器 `## 第一章 军事需求与现状分析` + H3 节标题 `### 军事需求分析`），并注明章容器由 `finalizer_agent` 在阶段9合并时插入，不由分章写作者自己写
- 校验工具层：`assemble/headings.py::_check_chapter_continuity()` 与 `gate3.py::_check_heading_continuity()` 均已修复空真值陷阱，显式区分"结构性缺失"（空列表 → ERROR）与"正常无编号"（非空列表全 None → 静默跳过）
- 审查清单层：`red-team-checklist.md` 新增"文档结构合规性"审查维度，要求人工核对 H2 章容器与 `outline.md` 章级条目的一一对应关系，作为工具校验之外的第三道防线
- 详见 `md-to-docx-pitfalls.md` 问题15（校验工具侧的具体代码修复）

## 问题2/2b：工作流中间数据混入最终交付物

**症状**：终稿正文中残留两类协作过程数据——(2) 写作者自声明区块（`### 写作者自声明（第 X 章）`及其字数/图数/表数/card_id 统计，全文约 25 处，每章一处）；(2b) 红队/审校批注引用块（`> [红队 RXXX 已改写]` 格式，全文约 8 处，散落在正文各处）。两者都是"生成给下一个处理环节看的中间数据"，却被当作正文内容留在了读者最终看到的报告里。

**根因（职责边界的契约缺口）**：`chapter_writer_agent` 的契约明确要求它产出"写作者自声明"，作为 `chapter_auditor_agent` 在 Phase B 比对时的客观依据——这个产出要求本身没有问题，自声明确实是审计环节的必要输入。问题出在**"谁负责在自声明完成使命后把它清除掉"这件事，在阶段7（写作）与阶段9（整合）两个阶段的契约文档之间，没有任何一方显式承接**：`chapter_writer_agent.md` 只定义了"如何产出"自声明，没有说明它的生命周期终点在哪里；`stage-9-finalize.md`（阶段9整合清单）在被识别问题之前，也没有把"剥离自声明/批注块"列为合并前的必做步骤。红队批注块（2b）是同一根因模式在阶段8（红队审查）产出物上的重演——红队审查过程中标注在正文旁的批注，同样缺少一个明确写入某个阶段契约的"清除责任人"。这是一种**流程设计上的责任真空**：每个阶段都清楚自己要"产出什么"，但相邻阶段之间"谁清理上一阶段的中间产物"没有被显式分配。

**修复**：
- 双重防线设计：`finalizer_agent` 在阶段9合并分章文件时主动剥离两类区块（主防线，已写入 `stage-9-finalize.md` §9.1 新增检查项）；`textstage/clean.py` 已新增兜底删除规则 R-12（自声明块整块删除）、R-14（红队/阶段9批注块删除）作为次防线，防止 `finalizer_agent` 漏剥离时仍有机会拦截——两条规则均已实现并通过自检测试（含围栏代码块内同名标题不误删等边界用例），双重防线已完整生效（详见 `md-to-docx-pitfalls.md` 问题17，及 `stage-9-finalize.md` §9.2 的规则表记录）
- 契约文档层：`chapter_writer_agent.md` 在自声明说明处明确标注其"审计阶段专用中间数据、不会出现在最终交付文档中"的生命周期终点，消除"这段写得挺详细，是不是本该留着"的误解空间
- 审查清单层：`red-team-checklist.md` 新增"文风终审"维度，将自声明/批注块残留列为专门检查项

## 问题3：规范文件示例诱导字面模仿

**症状**：写作 Agent 产出的正文中出现了四类"格式痕迹重于内容表达"的风格问题——(a) 写作者自声明残留（见问题2）；(b) `**主张**：……**证据**：……**推理**：……`这类字面加粗标签直接出现在论证段落中，而不是用连贯叙述体现同样的逻辑顺序；(c) 跨章自我指涉（如"本节承接上一小节的自声明"这类暴露写作过程本身的表述）；(d) 位置性指代（"上表""下图"）残留，与 Word 实际排版位置不符。

**根因**：这四个子问题表面上互不相关，但共享同一个根因模式——**"规范文档中用于教学示范的示例格式，被写作 Agent 当作应当逐字复制的正文格式模板"**。以子问题(b)为例：`writing-standards.md` 标准8"主张—证据—推理三角"的原"✅完整三角"示例，为了在教学场景下清晰地把三个环节区分开，使用了字面加粗标签`**主张**：`/`**证据**：`/`**推理**：`。这种呈现方式对"讲解这条标准是什么"是有效的，但写作 Agent 在实际写作时，从这份规范文档中读到的最后一段具体文字就是这三个标签——于是直接把标签抄进了最终正文，把一条本应是"组织顺序的隐性原则"的标准，退化成了一种"字面格式要求"。这是一类具有一般性的陷阱：**规范文档里的示例，比规范文字本身描述的原则，更容易被机械复制**——因为示例是具体的、可直接粘贴的文本，而原则是抽象的、需要理解后重新表达的要求，写作 Agent（尤其在缺少足够上下文推理深度时）倾向于走阻力最小的路径。

**修复**：
- `writing-standards.md` 标准8的示例改写为不含字面标签的连贯叙述段落，并新增说明"主张→证据→推理"是段落内部的组织顺序原则，不是要求逐字写出标签词
- 同一逻辑延伸检查了标准2（不确定性标注）的示例篇幅，收紧了过长的元评论式段落，避免同类"示例被当作模板抄袭"的风险以另一种形式重演（篇幅越长的示例，被整段复制的概率越高）
- `writing-standards.md` 新增位置性指代禁令，从根源解决子问题(d)
- `red-team-checklist.md` 新增"文风终审"维度作为产出后的检测防线，覆盖全部四个子问题
- **一般性启示（供未来维护规范文档时参考）**：撰写新的写作标准示例时，如果某个原则的呈现天然需要用到标签/编号/结构化格式来讲清楚，应当在示例旁**额外**给出一段"如果直接照抄这个格式会怎样"的反例或警示，而不是假设读者（包括 Agent）能自动区分"这是教学脚手架"与"这是格式要求"

## 问题6：编号系统三层硬编码

**症状**：章节编号（"第一章/1.1/1.1.1"）、图表编号（"图 X-Y/表 X-Y"）、正文交叉引用（"如图 X-Y 所示"）三类编号在最终 docx 中均以字面静态文本形式写入。报告在写作/审校过程中一旦发生任何章节增删、图表重排，这三类编号都需要全篇人工重新核对，没有 Word 原生"更新域"式的自动重排能力。

**根因**：`render/headings.py`（章节编号渲染）、`render/figures.py`/`render/tables.py`（图表编号渲染）、`render/paragraphs.py`（交叉引用文字渲染）三个渲染模块最初实现时，均选择了"直接拼接编号字符串写入段落"这一最简单直接的实现路径，而未接入 OOXML 提供的原生动态编号机制（`w:numPr` 多级列表、`SEQ` 域、`REF` 域）。这是一种**"架构级技术债因为初期可用而被长期忽视"**的典型模式：手动拼接编号在文档**首次生成**时结果是完全正确的——报告只要一次性从头到尾顺序生成，硬编码的编号天然就是连续递增的，不会露出破绽。缺陷只有在**后续编辑场景**（插入新章节、调整图表顺序、删除某个小节）下才会暴露——而这类编辑场景在开发/验证阶段往往被忽略或推迟到"以后再测"，导致"看起来能用就没人质疑底层机制是否健壮"，三处渲染模块的硬编码实现长期未被识别为问题，直到多轮实际项目积累了足够的章节重排/图表调整需求后才集中暴露。校验侧同样存在对应的滞后——`gate3.py::_check_figure_table_continuity()` 的现有校验逻辑只是比对字面编号数值有无跳号（`if seq != expected`），这类校验能发现"编号写错了"，但无法发现"编号写对了但机制是死的、下次编辑就会变错"这一更深层的问题，因为校验设计时同样是基于"硬编码是正常状态"的假设。

**修复**（由并行任务负责具体代码实现，本文档记录流程/设计层面的根因与方向）：
- 章节编号改用 `w:numPr` 多级列表机制，标题绑定列表层级而非拼接文字
- 图表编号改用 `SEQ` 域实现自动编号
- 正文交叉引用改用 `REF` 域绑定图表编号域生成的书签，引用文字随编号自动跟随更新
- 校验策略同步从"数值序列比对"转向"结构性存在检查"（校验编号是否真正绑定在动态域机制上，而非仅比较字面数字）
- 配套的写作规范调整：`writing-standards.md` 新增位置性指代禁令——因为 REF 域替换依赖被引用对象有一个可绑定的字面编号/书签，"上表""下图"这类无编号可绑定的指代方式与 REF 域机制天然不兼容，写作阶段就应避免
- **一般性启示**：涉及"编号/引用类"渲染功能时，评审代码是否用了动态域机制，不能只用"首次生成结果是否正确"作为验收标准，还需要额外验证"内容重排后再次生成，编号是否仍然正确"这一编辑场景，才能在问题积累到大规模返工之前发现硬编码实现的隐患
- 详见 `md-to-docx-pitfalls.md` 问题18（渲染模块侧的具体代码状态与实现方向）
