# 架构分析方法论指南

## 什么是架构分析

架构分析不是画一张"系统组成图"，而是**从多个视角拆解一个复杂系统的结构、关系、流动和约束**。
好的架构分析让读者理解：系统由哪些部分组成、它们如何协作、变化发生在哪里、瓶颈在哪里。

---

## 通用架构分析视角

根据报告主题，从以下视角中选择 3–6 个（不必全部使用）：

### 1. 业务/领域架构
- **问题**：业务/领域的核心流程是什么？从输入到输出经过哪些环节？
- **要素**：角色、活动、决策点、信息流、价值流
- **产出**：端到端流程图、决策树、价值链图

### 2. 技术/系统架构
- **问题**：支撑业务的技术系统如何分层？组件之间如何通信？
- **要素**：层次（基础设施/平台/应用/接口）、组件、协议、依赖
- **产出**：分层架构图、组件交互图

### 3. 数据架构
- **问题**：数据从哪里来、如何流动、在哪里存储、怎样被消费？
- **要素**：数据源、数据流、存储、转换、治理、质量
- **产出**：数据流图、数据模型图

### 4. 组织/治理架构
- **问题**：谁负责什么？决策权如何分配？协调机制是什么？
- **要素**：角色、职责、汇报线、委员会、流程
- **产出**：组织架构图、决策矩阵、RACI 表

### 5. 安全/风险架构
- **问题**：系统面临什么威胁？如何防护？失败后如何恢复？
- **要素**：威胁面、防护层、检测机制、响应流程、恢复策略
- **产出**：威胁模型图、防护层次图

### 6. 演进/迭代架构
- **问题**：系统如何随时间变化？不同变化速度的组件如何共存？
- **要素**：变化触发源、变化速度分层、测试-部署-回滚机制
- **产出**：演进路线图、分层迭代模型

---

## 架构分析的五个标准问题

每个架构视角（或本章核心技术章节）必须回答以下五个问题：

1. **位置**：该组件/子系统在总体架构中的位置是什么？上下游是什么？
2. **输入输出**：该组件接收什么输入？产生什么输出？格式和约束是什么？
3. **依赖**：该组件依赖哪些数据、链路、基础设施、外部系统？
4. **验证**：该组件如何被测试和验证？正确性、性能、安全性各用什么方法？
5. **反馈**：该组件的运行结果如何反馈到系统其他部分？如何触发迭代？

## 架构图绘制指南

### 图的前提

一张好的架构图应该满足：
- **自明性**：读者不看正文也能大致理解
- **层次感**：核心组件突出，辅助组件淡出
- **一致性**：同类型组件用同形状/同色系
- **有限性**：一张图不超过 15–20 个主要节点
- **尺寸随内容而非模板决定**：节点宽高应由文字量（字数×行数）动态估算，
  而非全篇套用同一固定 `w`/`h`。固定尺寸会导致长文本节点拥挤、短文本节点
  大片留白——出图工具应只允许"扩大"覆盖估算结果，不允许"缩小"

### 图的排版默认起点（3 条经验规律 + 1 条例外边界）

以下三条是出图时值得作为默认起点的排版规律（而非每张图各自摸索）：

1. **超过阈值数量的并列节点换行**：单行节点数超过 4-5 个时，改为多行平衡
   布局（尽量让各行数量接近，而非"前几行满、最后一行挤"）
2. **说明性文字并排双栏**：图例注释/证据脚注等说明性文字，优先左右并排
   而非纵向单栏堆叠，可显著压缩图的纵向总高度
3. **图例宽度贴合内容**：图例框宽度应按实际文字长度收紧，不铺满整行或
   使用固定大宽度

> **换行规律的例外边界（务必自查）**：换行只在"节点之间只有一种边关系"
> （纯顺序链/纯并列/纯层级）时安全。若某组节点同时承担两种及以上边角色
> （既是链条中的一环，又是某个下游汇聚点的输入源），换行会让"行内相邻
> 关系"与"另一种边角色"的走线在 orthogonal 路由器下产生视觉歧义——
> 此时应保持单行，换行前先画草图确认相邻关系不会造成误导。

### 图的标注

每张架构图应包含：
- 图标题（图 X-Y：描述）
- 图例（颜色/形状/线型的含义）
- 关键注释（约束条件、前提假设、数据来源）

### 图的检查

- [ ] 图中的每个节点在正文中都有对应说明？
- [ ] 图中的每条连线（数据流/依赖）在正文中都有解释？
- [ ] 图与图之间的逻辑一致（同一对象在不同图中名称相同、关系一致）？
- [ ] 图的复杂度与章节篇幅匹配（不要用一张极其复杂的图来"省文字"）？
- [ ] **容器（分组框）在 XML 中是否声明于其子节点之前？** drawio 按声明
      顺序绘制，后声明的图形会盖住先声明的——分组框若写在子节点之后，会
      整个盖住子节点（机器门禁 G1/G2/G6/G7/G10a/G12 均不检查绘制顺序，
      只有实际导出 PNG 用眼看才能发现）
- [ ] **画布节点文本是否混入了图号/章节号等结构性元信息？**（如"第4章"
      "图3-1"字样）节点文本只应承载该节点自身内容，报告中该概念对应第几
      章/引用哪张图的关系应写在正文 Markdown 里，不写进画布——大纲章节
      编号在写作中随时可能调整，画布里手写死的章号会静默腐化且无报错
- [ ] **是否存在需要精确绕行的边（跨越第三方节点的反馈边/闭环边）？**
      若有，必须显式给出 `waypoints` 途经点坐标（对应 drawio 的
      `<Array as="points">`），不能只靠 `exitY`/`entryY`/`curved=1` 等
      样式提示——这些提示依赖人在编辑器里真实拖拽过的交互历史，纯脚本
      批量生成时路由器不会主动采纳，边线可能直接穿过居中的兄弟节点文字
- [ ] **每次导出 PNG/SVG 预览之后，是否还要再跑布局门禁？** 若是，应先
      确认 `.drawio` 源文件的字节内容仍与最近一次生成脚本输出一致——
      交互式工具（draw.io 桌面版/在线版）执行"导出"时可能伴随隐式写回，
      有污染源文件的实测先例。稳妥流程：完成全部内容设计与迭代（此阶段
      只跑布局门禁，不导出预览）→ 门禁全绿后统一做一轮 PNG/SVG 导出 →
      如需再改，回生成脚本改（不手动碰 `.drawio`）→ 重新生成 → 重新跑
      门禁，避免"改一点导出看一点"的频繁交替

## 从原方法论中抽象出的通用模式

### 模式 1：闭环反馈

几乎任何领域的深度分析都可以用一个闭环图来贯穿：

```
[触发/变化] → [感知/识别] → [分析/决策] → [行动/执行] → [效果评估] → [知识沉淀] → 回到[触发/变化]
```

根据主题调整各环节的名称和具体内容。

### 模式 2：分层迭代

大多数复杂系统都有不同速度的变化层：

| 层级 | 变化速度 | 典型动作 | 验证强度 | 部署策略 |
|---|---|---|---|---|
| 快速响应 | 小时–天 | 参数调整、规则更新 | 轻量校验 | 全局快速生效，可回滚 |
| 中期演进 | 天–周 | 组件升级、模型微调 | 自动化+对抗测试 | 先试点后推广 |
| 长期升级 | 周–月 | 架构变更、新系统集成 | 全场景验证 | 分级灰度 |

> 根据主题调整：企业产品可以是"热修复/功能迭代/架构升级"，公共政策可以是"紧急令/行政令/立法"。

### 模式 3：多视角架构拆解

不要只从一个角度描述系统。至少从 3 个视角交叉分析，每个视角有专属图表。

## 不同领域的架构适配示例

### 企业/产业分析
- 业务架构：客户旅程 → 价值交付流程
- 技术架构：IT 系统分层 → 数据中台 → 业务中台
- 竞争架构：市场格局 → 差异化定位 → 护城河
- 财务架构：收入模型 → 成本结构 → 现金流

### 公共政策分析
- 法律架构：上位法 → 行政法规 → 地方细则
- 行政架构：中央 → 省市 → 基层的权责与资源
- 利益相关方架构：政府 / 企业 / 公众 / 媒体的博弈关系
- 执行架构：政策工具 → 试点 → 评估 → 推广

### 技术/产品评估
- 功能架构：核心功能 → 扩展功能 → 接口
- 技术架构：前端 → 后端 → 数据 → 基础设施
- 安全架构：身份认证 → 授权 → 审计 → 加密
- 迭代架构：需求管理 → 开发流程 → 测试 → 部署 → 监控
