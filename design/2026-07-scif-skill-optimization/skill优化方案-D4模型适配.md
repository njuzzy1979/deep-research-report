# 第一部分：为什么 DeepSeek V4 会不遵守 skill 规定

> 这是用户提出的核心问题，本节直接、完整地回答。

## 结论先行

**主要不是模型不听话，而是 skill 在这个位置根本没有下达可执行的指令。归因为流程设计因素 70%、模型能力因素 30%。应对措施应当是加护栏，而不是换模型。**

---

## 一、流程侧的三个结构性空洞（70%）

### 空洞 1：阶段 9 是全流程唯一没有模型档位感知的阶段

skill 的模型能力档机制覆盖了 13 个文件、133 处引用。但逐一定位后发现，它们**全部**作用于阶段 1（检测配置本身）、阶段 7（写作/审计）和阶段 8（红队）。

**实测**：`references/stage-9-finalize.md` 与 `agents/finalizer_agent.md` 两个文件中，`tier` / `capability_tier` / `model-profile` 的出现次数**都是 0**。

也就是说，DeepSeek V4 在阶段 9 收到的指令与 Claude 收到的**逐字相同**。能力档机制在此处完全不存在——谈不上"没遵守"。

### 空洞 2：失败路由表存在，但物理上没有进入违纪者的上下文

`agents/finalizer_agent.md:55-63` 定义了一张相当完善的 `failure_step` 固定路由表，6 个失败枚举值各有明确路由动作。其设计意图（同文件第 12 行）就是"你不需要自己诊断哪一步出错，只需查表"。

问题在于：**这张表写在子 Agent 的定义文件里**，只有当 orchestrator 分派 `finalizer_agent`、由该 Agent 读取自身定义时才会加载。

而实际发生的是：orchestrator **亲自运行了 `finalize_pipeline.py`**——此时它从未读过这个文件，表对它不存在。

`SKILL.md` 的 orchestrator 剧本与 `references/multiagent-orchestration.md` 全文，**没有任何一条要求 orchestrator 在自行执行阶段 9 脚本前先读取该路由表**。这是一个纯粹的编排设计遗漏。

### 空洞 3："禁止自行绕行"这条纪律在 skill 中不存在

`references/multiagent-orchestration.md:169-173` 确实有一节"禁止的操作"，包含"不得默认放行""不得自动选择路径"。但该节的上下文是"写审对抗 2 轮上限后的 P0 死锁处理"，**只约束阶段 7**。

`SKILL.md:197-216` 的 20 条反例清单逐条检查过，**没有一条禁止 orchestrator 用自写脚本替代 skill 管线**。

当脚本报错、用户在等交付时，模型面对的是一个规范上的**空白区**——它自写了一个正则合并脚本，严格来说没有违反任何一条写下来的规则。

---

## 二、模型侧确实存在的部分（30%）

必须承认模型因素真实存在，但它的作用面比直觉小得多，且可以精确界定。

本次运行加载的 `model-profile.local.json` 是 tier B，四个开关中：
- `hard_rule_budget=5`（红线砍至 5 条）
- `envelope_nonce=true`
- `template_fill_mode=on`

三个生效；第四个 `max_output_tokens=380000` 使 `phase_a_mode` 派生为 `free`——**与 Claude 完全相同**。

而这四个开关**全部只作用于阶段 7 的 prompt 构造**。

因此在阶段 9，DeepSeek V4 与 Claude 拿到的输入是同一份，输出的差异只能归因于模型自身的行为倾向：**在既定流程失败时，是倾向于回读规范文档寻找路由，还是倾向于直接编写代码解决问题**。

DeepSeek V4 选择了后者，并**连续选择了两次**（先自写正则合并，再自写 python-docx 生成）。这是真实的模型差异，不应粉饰为纯流程问题。

### 一处必须如实标注的置信度限制

skill 的档位判定实际是**按模型名做正则匹配**（`scripts/model_profile.py:109-150` 的 `_MODEL_RULES`）。

而这恰恰是设计方案（`design/model-compatibility-optimization-plan.md:83`）中被**明确否决**的方案，理由是"模型名不稳定"：

> "能力分档用配置声明，不用运行时探针……被否决的替代：运行时能力探针；**按模型名字符串推断（模型名不稳定）**"

这意味着"DeepSeek V4 = Tier B"这个标签本身是配置表里的一行硬编码，不是能力实测结果。

**因此上述 30% 的估计带有不确定性——我们观察到的是"这个模型在这次运行中这样做了"，而不是"Tier B 模型必然这样做"。**

---

## 三、换成 Tier A 模型能否避免？——只能降低概率，不能结构性避免

坦率说：**大概率能避免这一次，但不能保证下一次。**

理由是同样的空洞对 Claude 同样敞开——阶段 9 没有档位感知，路由表同样不在 orchestrator 的上下文里，"禁止自行绕行"这条规则对 Claude 也同样不存在。

Claude 在"遇到既定流程失败时倾向于回读规范"这一点上表现更稳，但这是**概率优势，不是结构保证**。把交付质量押在"这个模型比较自觉"上，等于把已经暴露的结构缺陷重新盖起来。

### 本次事故提供了一条方向相反的强证据

**最终成功的路径，是把任务分派给了 `finalizer_agent`——一个跑在 Haiku 上的、能力远低于 DeepSeek V4 的模型。**

它不仅正确调用了 `finalize_pipeline.py`，还顺带修掉了 `figure_gate.py` 的 AttributeError 和 outline 键名不匹配两个底层 bug，最终跑出 `overall_pass:true`。

它做对的原因不是更聪明，而是它拿到的 prompt 里有：**收窄到一句话的职责边界、唯一执行入口、以及那张 `failure_step` 固定路由表**。

> **同一个任务，弱模型 + 强约束的结果，优于强模型 + 无约束。**

这条实证直接决定了处方的方向。

---

## 四、结论性判断：加护栏

应当加护栏，不换模型。

换模型只是把 30% 的那部分风险换掉，剩下 70% 的空洞原样保留，且会在下一次遇到未被覆盖的阶段时以另一种形态复发。

### 但必须诚实说明护栏的天花板

审查层对本方案的护栏部分给出了尖锐且成立的批评：

- `references/multiagent-orchestration.md:128` 自述"**无 Hook 级强制**：所有 Agent 边界与预承诺纪律都是 prompt-level，无确定性 PreToolUse hook 拦截"
- 实测 skill 目录无 `.claude/hooks`，用户级 settings.json 无 hooks 段——**机器强制层在这个系统里完全不存在**
- 本方案 15 个护栏条目中 **12 个是纯文档约束（80%）**，仅 3 个可做成机器强制
- 对证据 D 八步做反事实推演：真正需要拦住的第 2/3/4/5 步，纯文档护栏**0 步能拦住**

**"20 条反例没拦住，第 21 条凭什么能拦住？"**——这个质疑成立。第 21 条不会被强制注入 orchestrator 的上下文，继承不了 `finalizer_agent` 成功的那个因素。

**因此本方案把预算从文档层转向了四条机器强制项**（详见 D2 文档）：失败时半成品清理、docx 回读校验、provenance sidecar、delivery_checklist 补 output_dir 贯通。

**若只能做两件事，就做"失败时不留半成品"和"docx 回读校验"。**

# 第二部分：模型档位感知设计

## D4-3（P3）Tier 感知的流程严格度

**实测约束**：`multiagent-orchestration.md:105` 明写"正交的**第二维**"、`:107` "两者独立生效"、`:89` 标题"**二维**决策矩阵"。插入"第三维"与已成文措辞直接矛盾。

**定案：并入 §7.5 表格作为第三列**（更干净），而非独立成节。

| 严格度项 | Tier A | Tier B | Tier C |
|---|---|---|---|
| 阶段起始工具集复述 | 可选 | 强制 | 强制，须附路由表出处 |
| 连续无回报步数上限 | 不限 | ≤3 步 | ≤2 步 |
| 每步产物校验 | 阶段末统一 | 强制逐步 | 逐步 + 贴 stdout |
| 失败态处理 | 允许自主重试 1 次 | **强制停机询问** | 停机 + 附完整 JSON |
| 自写代码 | 允许（须在 CP 呈报） | **禁止** | 禁止 |
| 能力边界判断 | 可自主判定 | **须先跑最小验证命令** | 同 Tier B |
| 非确定性输出重试 | ≤2 次自主判定 | **白名单制** | 白名单制 |

**重试白名单核心原则：确定性失败禁止重试。** 脚本 exit≠0 是确定性失败——重跑必然同样失败，重试只是拖延，且极易诱发"换个方式绕过去"。事故第 1-3 步正是这一模式。

> **诚实标注**：此表是**纯文档约定**，未落到 `model_profile.py`。它与既有的 §7 上表一样只能靠模型自律——**而这恰恰是本次事故的失效模式**。列入 P3，不计入有效交付项。

## D4-10（P0）`model_profile.py` 死代码修复

**实测**（Python AST 解析）：

```
format_text_report defined: False
funcs: ['_detect_model_from_env', '_normalize', '_write_local_override',
        'auto_configure', 'derive_phase_a_mode', 'load_profile', 'main',
        'record_degradation', 'resolve_collaboration_mode']
```

`:400` 是 `_write_local_override()` 的 `return out_path`，而 `:401-419` 的 `lines = [...]` 到 `return "\n".join(lines)` **位于 return 之后，是不可达死代码**——这段本应是 `format_text_report(profile)` 的函数体，函数定义头在某次编辑中丢失。

而 `:507` 无条件调用它：

```python
if args.json:
    print(json.dumps(profile, ensure_ascii=False, indent=2))
else:
    print(format_text_report(profile))   # NameError
```

**后果**：`python scripts/model_profile.py`（无参，即 `SKILL.md:100-104` 与 README 展示的**基本用法**）**必抛 NameError**。

**为什么至今未被发现**：`references/stage-1-init.md:43-47` 的步骤 3 用的是 `--json`，走了另一分支——**它恰好只在文档教用户执行的那条路径上崩，不在 orchestrator 实际走的路径上崩**。

**方案**：在 `:401` 前插入函数定义头 `def format_text_report(profile: dict) -> str:`，并将 `:401-419` 整体缩进对齐为其函数体。**零逻辑改动，纯结构修复，15 分钟。**

**优先级判定为 P0 的理由**：Tier 感知门禁是本方案唯一的真机器护栏，而其载体脚本的基本用法就崩——不修则唯一的机器护栏是坏的。

## D4-7 orchestrator 纪律（合并 证据D + P11）

**合并理由**：P11（orchestrator 把红队 R13 的"36 张数据图缺失"误判为"超出工具链能力"，而 matplotlib 完全可用）与证据 D 是**同一个失效模式的两个实例**——orchestrator 在遇到障碍时**自行做出了一个规范未授权的判断，且该判断无需任何验证即可生效**：

- 证据 D：判断"脚本走不通" → 自写替代方案生效，无验证
- P11：判断"工具链不支持" → 降级生效，无验证（实际 `python -c "import matplotlib"` 一行即可证伪）

两者共用同一条修复：**任何 orchestrator 的自主判断（能力边界/流程绕行）必须先执行可验证动作并贴出结果，否则视为无效判断**。

拆成两个修复项会导致两处各写一套护栏，且必然漂移。

**落地方案见 D2 文档**（三层护栏）。

**附带修复**：`agents/data_chart_agent.md:63` 现文"matplotlib 代码运行出错 → 重试一次，仍失败则上报 orchestrator 降级决策"，追加 P11 专项——`orchestrator 收到降级请求时，须先执行 python -c "import matplotlib; print(matplotlib.__version__)" 并贴出结果，方可判定为工具链能力问题；未执行验证的降级判定无效`。

## D4-8 长耗时操作治理（合并 P3 + P4）

**合并理由**：P3（Tier B × 多 Agent 的超时/API 错误/非确定性）与 P4（MinerU 大文件超时）表面在不同阶段，根因同为**"单次调用无界等待，超时后无规定动作，于是上游把'等太久'误读为'能力不足'并绕过"**——这正是 P11 的诱发路径。三者串成一条链，修一处不修另一处，链条仍成立。

**现状实证**：`multiagent-orchestration.md:55-56` 只有两行超时规定（>15 分钟终止、关键路径重试满 2 次），**无 tier 区分、无失败类型区分、无外部 CLI 超时规定**。

**重要澄清**：`stage-2-collection.md:183` 说明 `mineru_parse.py` 已内置超限自动分片（>200 页/200MB）。**因此 P4 的残留问题不是分片，而是"分片后单片仍超时时无规定动作"**——不要重复实现已有功能。

**实施注意**：`mineru_parse.py` 位于**另一个 skill**（`skills\mineru\scripts\mineru_parse.py`），由 `tool-paths.json` 的 `mineru.absolute_path` 声明。文档中引用时**必须带 tool-paths.json 解析步骤**，不能写成本 skill 的相对路径。

## D4-9 阶段 2 门禁自适应（合并 P5 + P6）

**合并理由**：两者同为**"阶段 2 的门禁是硬编码常量，不随来源类型自适应，且分级一旦写入无修订环节"**。

- **P6 实证**：`stage-2-collection.md:76-77` 的 80% 门槛（**唯一带 STOP 的门槛**），分母定义为"`source_type` 为 PDF/网页且非'在线资源'的条目数"——**网页型来源被计入分母但天然难以"下载"为本地文件**，导致网页密集型选题必然触发 STOP（本次 112 条来源仅 13 篇 PDF 可下载，11.6%）。

**方案**：
1. `:76` 分母定义改为**按 source_type 分桶**——PDF/Office 类适用 80% 门槛；网页类适用"已 extract 为 markdown 且落盘 `research/extracted/`"的 80%。

3. `agents/source_collector_agent.md`：初始分级不得默认全 D——无法判定时写 `C` 并在 notes 标注"待阶段 3 判定"，避免全 D 导致下游全面阻塞。

**实施注意**：CSV 字段行在 `:148` 与 `:169` **重复出现两次**，禁止全文替换。原方案引用的 `:244` **不是门槛而是收尾自检清单项**（无 STOP 语义），措辞须改。
